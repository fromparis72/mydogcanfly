   - **Preview Pages — le nom trompe, ce n'est PAS une preview.** Le projet Cloudflare Pages `mydogcanfly-v2-preview` (celui que cible `npm run release` avec `--branch=main`) a pour domaines personnalisés actifs, SSL activé : **`mydogcanfly.com` et `www.mydogcanfly.com`.** C'est donc, malgré son nom, **le projet Pages de production réelle du site.** `npm run release` déploie directement en production, jamais sur un environnement isolé. Aucun dépôt Git n'y est connecté (déploiement uniquement par `wrangler pages deploy` manuel, jamais automatique) — confirmé sur l'onglet Settings du projet, cohérent avec le fait qu'aucun `npm run release` n'a été exécuté depuis les derniers commits (New York, Option B) : **la production n'a reçu ni l'un ni l'autre à ce jour.**
   - **Découverte annexe, hors du périmètre de la question posée mais à signaler** : il existe un **second** projet Pages, nommé simplement `mydogcanfly`, connecté au dépôt GitHub `fromparis72/mydogcanfly` avec déploiement automatique activé sur la branche `main` (chaque push déclenche un déploiement). Sa commande de build est `hugo`, sortie `public` — **c'est le site Hugo legacy, pas le V2 Astro** ; les fichiers `packages/ui/**` (dont `fiche.astro`) n'entrent dans aucun build de ce projet. Il republie donc le même Hugo à chaque push (y compris nos commits Option B/New York, sans effet sur son contenu, puisque Hugo ne lit pas ces fichiers) sur `mydogcanfly.pages.dev`, **sans domaine personnalisé attaché** — pas exposé sous `mydogcanfly.com`. Aucun risque de sécurité identifié pour Option B (le patch ne peut pas être exposé par ce canal), mais c'est un pipeline actif et oublié qui republie une URL publique à chaque commit — à traiter dans le Lot 5 (migration Hugo→V2, document 07) : le conserver, le désactiver, ou le réutiliser consciemment.
   - **Conclusion pour ce dossier** : `npm run release` (site) déploie **toujours et uniquement** en production (`--branch=main` sur le projet Pages `mydogcanfly-v2-preview`, qui porte les domaines personnalisés `mydogcanfly.com`/`www.mydogcanfly.com`) — ce script ne doit jamais servir à tester quoi que ce soit, seulement à publier une fois la validation faite. Le déploiement Option B via ce même mécanisme reste, comme prévu, sans risque d'avoir déjà atteint la production : rien n'a été poussé côté Pages production à ce jour.
   - **Correction (contre-revue Codex, 10/08/2026, tour 3)** : une version précédente de cette conclusion affirmait qu'aucune preview Pages isolée n'existait et qu'il en faudrait créer une nouvelle (branche dédiée + déploiement Git connecté). **C'est inexact.** Le projet `mydogcanfly-v2-preview` étant un projet Direct Upload (aucun dépôt Git connecté, confirmé ci-dessus), il accepte nativement des déploiements par branche arbitraire via `wrangler pages deploy <dist> --project-name=mydogcanfly-v2-preview --branch=review-<SHA>` — cette commande produit une URL de preview isolée en `<branche>.mydogcanfly-v2-preview.pages.dev`, distincte du domaine de production, sans toucher aux domaines personnalisés ni nécessiter de raccordement Git. **Condition avant utilisation** : vérifier dans l'onglet Settings du projet que la branche de production configurée est bien `main` — c'est cette configuration qui garantit qu'un déploiement sur `--branch=review-<SHA>` ne remplace pas la production. Cette vérification n'a pas encore été faite (à ajouter à la liste ci-dessus). Une fois confirmée, cette commande devient la méthode standard pour toute validation en ligne avant `npm run release`, remplaçant les options précédemment envisagées (déploiement direct en production sous contrôle, notamment) pour tout ce qui peut être testé ainsi.
